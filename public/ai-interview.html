Why Hybrid over Pure Vector?

  • Exact match matters — "NVDA revenue growth" needs literal ticker match
  • Financial terms — "10-K" or "gross margin" are keyword problems
  • RRF fusion — parameter-free, well-studied, within a few % of learned fusion

Single PostgreSQL for Everything

  • Structured data (companies, financials)
  • Vector embeddings (pgvector)
  • Full-text search (tsvector/tsquery)
  • Long-term memory (notes table)
Fallback: If embedding fails, gracefully degrades to sparse-only search.

TMeta Migration Motivation

Why Migrate from RDS to KV?

Problems with RDS

  • Full-table scan — slow queries under load on cache miss paths
  • Architecture divergence — internal/external used different DB backends
  • Operational overhead — MySQL schema management, index tuning

Target: ByteKV

  • Company-internal distributed KV store
  • Better suited for key-based lookup patterns
  • Unified architecture across deployments
  • Simpler operational model at scale

Constraints

  • Zero downtime — TMeta is on the critical path for all TOS operations
  • ~200K QPS must be maintained throughout
  • Data consistency must be verified before cutover
  • Rollback must be possible at every phase
Principle: Safety over rollout simplicity. No big-bang cutover — every phase must be independently reversible via dynamic config.

Key Implementation Details

  • Interface abstraction — BucketDB, AccountDB decouple business logic from storage backend
  • DBHub factory — assembles SQL / KV / MigrationDB mode via dynamic config
  • MigrationDB wrapper — same interface, orchestrates dual-write and read delegation
  • Write strategy — primary first, secondary async; secondary failure: log + alert, don't fail request

Consistency Verification

  • Full scan — migration tool compares all records in RDS and KV
  • updatedAt-based repair — newer record wins, sync to older store
  • Re-verify — repeat until zero mismatches
  • Canary rollout — one region first, monitor error rate & latency
Rollback at every phase: Switch dynamic config (TCM) to revert read/write targets. No deployment needed.
